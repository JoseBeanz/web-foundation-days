Reflection
The most difficult concept for me was concurrency and preventing double-booking. Before this course I thought of "checking if a seat is free" as a simple if statement, and it took the transactions material — plus trying to reason about two requests arriving at the same millisecond — before I understood why a check-then-write is unsafe. What helped was working through the URL shortener example: the idea that a constraint in the database (the primary key there, the UNIQUE constraint here) is the final guarantee, while application logic is the fast path. Once I saw correctness as "the database refuses the second write," the design became much easier to reason about, and I could stop trying to make the application code perfect and instead make it safe.

For my capstone, the feedback I received was that my architecture diagram had components I could not fully justify, and that I should show the request in the Network tab during the demo. Based on that, I would improve two things: trim the diagram to only components that answer a named problem (the "if you cannot name the problem, the component does not belong" rule), and practice the live demo with the browser dev tools open so I can point at real requests and status codes instead of describing them. I would also add estimates to the capstone write-up, since the rubric weights scaling evidence heavily and I had left them implicit.

Next, I want to build a real backend with Node.js and Express to turn my API design into working code, then connect it to PostgreSQL using the free SQLBolt lessons and the PostgreSQL tutorial. After that, I plan to learn React so I can build larger interfaces from reusable components, and to keep practising system design with The System Design Primer and ByteByteGo. Fluency comes from repetition, so my goal is one small design or backend exercise per week rather than one big push.
